# Patching ECS Fargate tasks with the Falcon Container sensor

This folder is a hands-on guide to every supported way of adding the CrowdStrike Falcon Container sensor to an Amazon ECS Fargate workload. Each sample can be run **locally from your workstation** with the AWS CLI and Docker, or from CI. The [pipeline](../.github/workflows/cs-ecs-fargate-demo.yaml) runs the same steps.

| Sample | Method | What changes | Local guide |
|---|---|---|---|
| [01](01-falconutil-patched-image) | `falconutil patch-image` | Your **image**: the sensor is built into a new image. The task definition only adds `SYS_PTRACE`. | [Run it locally](01-falconutil-patched-image/README.md#run-it-locally) |
| [02](02-terraform-module) | Terraform module | Your **task definition**, generated by [`CrowdStrike/terraform-aws-ecs-fargate`](https://github.com/CrowdStrike/terraform-aws-ecs-fargate) | [Run it locally](02-terraform-module/README.md#run-it-locally) |
| [03](03-task-definition-patch) | Patching utility on task definition JSON | Your **task definition**, rewritten by the utility in the sensor image | [Run it locally](03-task-definition-patch/README.md#run-it-locally) |
| [04](04-cloudformation-patch) | Patching utility on CloudFormation | Your **template**: each `AWS::ECS::TaskDefinition` is rewritten | [Run it locally](04-cloudformation-patch/README.md#run-it-locally) |

The [detection container](../demo/detection-container) guide uses method 01 to run CrowdStrike's detection container and generate real detections.

## Choosing a method

- **Patch the image (01)** when you control the build. You can deploy the result with any tool, and the task definition stays almost untouched. The trade-off is that you rebuild the image to update the sensor.
- **Patch the task definition (02-04)** when you don't want to modify images, or you deploy third-party images. A Falcon **init container** copies the sensor into a shared volume at task start, and your container launches through the Falcon entrypoint wrapper. To update the sensor, change the sensor image tag; the app image stays the same.
  - Use **02** if you manage ECS with Terraform.
  - Use **03** if you register task definitions as JSON (AWS CLI, `amazon-ecs-deploy-task-definition`, CodePipeline).
  - Use **04** if you use CloudFormation, CDK synth output or SAM.

Every method needs the `SYS_PTRACE` Linux capability on each protected container, and outbound network access from the task to the CrowdStrike cloud.

## One-time local setup

### 1. Tools and access

- **AWS CLI v2**, signed in to the target account, plus **Docker** with `buildx`. The sensor mirror uses `docker buildx imagetools`. Docker Desktop includes buildx; on Colima, run `brew install docker-buildx`.
- `jq`, `yq` (only needed for sample 04) and `envsubst` (part of `gettext`).
- **A CrowdStrike API client** with *Sensor Download: Read* and *Falcon Images Download: Read*. Create one in the Falcon console under **Support and resources → API clients and keys**.

### 2. Environment

Run these in the shell you'll use for the samples. The commands read the client secret without echoing it, so it doesn't land in your shell history.

```bash
export AWS_REGION=us-west-2
export NAME_PREFIX=ecs-fargate-demo                 # matches the bootstrap stack; change if you use your own names
export FALCON_CLOUD=us-1                             # us-1 | us-2 | eu-1 | us-gov-1 | us-gov-2
export FALCON_SENSOR_TAGS=ecs-fargate-demo         # optional sensor grouping tags (comma-separated)
export FALCON_CLIENT_ID="<your API client ID>"
read -rsp "Falcon client secret: " FALCON_CLIENT_SECRET && export FALCON_CLIENT_SECRET && echo

export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export REGISTRY=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com

# CrowdStrike's helper for the sensor registry, pinned to a release
curl -fsSLO https://raw.githubusercontent.com/CrowdStrike/falcon-scripts/v1.14.0/bash/containers/falcon-container-sensor-pull/falcon-container-sensor-pull.sh

# Your CID, including the checksum, read with the same API client
export FALCON_CID=$(bash falcon-container-sensor-pull.sh --region "$FALCON_CLOUD" --get-cid)
```

### 3. A Docker config that stores credentials in the file

`falconutil` and the patching utility read registry credentials straight from Docker's `config.json`. They can't use credential helpers such as Docker Desktop's `desktop`/`osxkeychain` store. A throwaway config directory avoids the problem:

```bash
export DOCKER_CONFIG=$(mktemp -d)
aws ecr get-login-password | docker login --username AWS --password-stdin "$REGISTRY"
```

Docker warns that the password is stored unencrypted. That's expected: the file lives in a temporary directory, so delete it when you're done.

### 4. ECR repositories and an execution role

If you ran [`bootstrap/setup.sh`](../bootstrap/setup.sh), these already exist: the `${NAME_PREFIX}/app`, `app-falcon-patched`, `falcon-container` and `detection-container` repositories, and the `${NAME_PREFIX}-task-execution` role. Otherwise, create the minimum:

```bash
for repo in app app-falcon-patched falcon-container; do
  aws ecr create-repository --repository-name "$NAME_PREFIX/$repo" >/dev/null
done
aws iam create-role --role-name "$NAME_PREFIX-task-execution" \
  --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs-tasks.amazonaws.com"},"Action":"sts:AssumeRole"}]}' >/dev/null
aws iam attach-role-policy --role-name "$NAME_PREFIX-task-execution" \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy
# The JSON samples use awslogs-create-group, which also needs logs:CreateLogGroup
aws iam put-role-policy --role-name "$NAME_PREFIX-task-execution" --policy-name create-log-groups \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"logs:CreateLogGroup","Resource":"arn:aws:logs:*:*:log-group:/ecs/'"$NAME_PREFIX"'-*"}]}'
```

```bash
export TASK_EXECUTION_ROLE_ARN=arn:aws:iam::$ACCOUNT_ID:role/$NAME_PREFIX-task-execution
```

### 5. Mirror the Falcon Container sensor into ECR

The init container methods (02-04) pull the sensor image when the task starts, so it has to live in a registry the execution role can read. Copy it once per sensor release:

```bash
SENSOR_IMAGE=$(bash falcon-container-sensor-pull.sh --region "$FALCON_CLOUD" --type falcon-container --get-image-path | tail -n 1)
export SENSOR_VERSION=${SENSOR_IMAGE##*:}            # e.g. 8.10.0-8002; add --version to pin a release

# Without --platform the multi-architecture image (x86_64 + ARM64) is copied
bash falcon-container-sensor-pull.sh --region "$FALCON_CLOUD" --type falcon-container \
  --version "$SENSOR_VERSION" --copy "$REGISTRY/$NAME_PREFIX/falcon-container" --copy-omit-image-name

export FALCON_IMAGE=$REGISTRY/$NAME_PREFIX/falcon-container:$SENSOR_VERSION
```

To see the available releases, run `bash falcon-container-sensor-pull.sh --region "$FALCON_CLOUD" --list-tags`.

### 6. Build and push the sample app

```bash
export APP_IMAGE=$REGISTRY/$NAME_PREFIX/app:local
docker build --platform linux/amd64 -t "$APP_IMAGE" app
docker push "$APP_IMAGE"
```

Run this from the repository root. On Apple Silicon, `--platform linux/amd64` builds an x86_64 image to match the samples' `X86_64` runtime platform.

You're now ready for any of the samples.

## Running and verifying a protected task

The samples only register task definitions. Before running one, give its log group a retention policy. Samples 01 and 03 and the detection container use `awslogs-create-group`, which creates groups that keep logs forever. Samples 02 and 04 already set 7 days.

```bash
LOG_GROUP=/ecs/$NAME_PREFIX-task-definition-patch      # or -patched-image, -detection-container
aws logs create-log-group --log-group-name "$LOG_GROUP" 2>/dev/null || true
aws logs put-retention-policy --log-group-name "$LOG_GROUP" --retention-in-days 7
```

To start a task, you need a cluster and a subnet with outbound internet access. The bootstrap creates both: a cluster that defaults to Fargate Spot, and public subnets whose security group has no inbound rules.

```bash
out() { aws cloudformation describe-stacks --stack-name ecs-fargate-demo-bootstrap \
          --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }
export CLUSTER=$(out DemoClusterName) SUBNETS=$(out DemoSubnetIds) SECURITY_GROUP=$(out DemoSecurityGroupId)

TASK_ARN=$(aws ecs run-task --cluster "$CLUSTER" \
  --capacity-provider-strategy capacityProvider=FARGATE_SPOT,weight=1 \
  --task-definition "$NAME_PREFIX-task-definition-patch" \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNETS],securityGroups=[$SECURITY_GROUP],assignPublicIp=ENABLED}" \
  --query 'tasks[0].taskArn' --output text)
aws ecs wait tasks-running --cluster "$CLUSTER" --tasks "$TASK_ARN"
echo "Task ID (Falcon Pod ID): ${TASK_ARN##*/}"
```

Swap in the task definition family of the sample you ran:
- `-patched-image`
- `-terraform-module`
- `-task-definition-patch`
- `-cloudformation-patch`

To check that the sensor connected:

- **Falcon console:** go to **Host setup and management → Manage endpoints → Host management**, add a **Pod ID** filter, and set it to the ECS task ID. A host with a Host ID (AID) means the sensor registered.
- **Task logs:** check `/ecs/${NAME_PREFIX}-<sample>` in CloudWatch Logs. A container that exits straight away usually means the entrypoint or command is wrong (see below).
- **ECS Exec** (optional): this needs `enableExecuteCommand` on the task and a task role with the SSM messages permissions. For init container tasks, run `/tmp/CrowdStrike/rootfs/bin/falconctl -g --aid` inside the app container. On musl-based images such as Alpine, prefix it with `/tmp/CrowdStrike/rootfs/lib64/ld-linux-x86-64.so.2 --library-path /tmp/CrowdStrike/rootfs/lib64`.

Stop the task when you're done:

```bash
aws ecs stop-task --cluster "$CLUSTER" --task "$TASK_ARN" >/dev/null
```

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `falconutil` or the patching utility can't pull an image (`unauthorized`, `no basic auth credentials`) | Docker is using a credential helper. Use a throwaway `DOCKER_CONFIG` ([setup step 3](#3-a-docker-config-that-stores-credentials-in-the-file)). For the patching utility, check that `-pulltoken` is current: ECR tokens expire after 12 hours. |
| `Parameter validation failed` or `Unknown parameter in input` when registering a patched definition | The input was exported from an existing task definition. Remove the read-only fields before patching: `taskDefinitionArn`, `revision`, `status`, `requiresAttributes`, `compatibilities`, `registeredAt`, `registeredBy`, `deregisteredAt`, and `tags` if empty. See [sample 03](03-task-definition-patch/README.md#patch-an-existing-task-definition). |
| The app container exits immediately after the init container completes | The Falcon wrapper couldn't work out your entrypoint. Set `entryPoint` and/or `command` explicitly in the container definition, or let the utility read them from the image with a valid `-pulltoken`. |
| A task with `readonlyRootFilesystem: true` fails to start or the sensor can't write | The sensor needs a writable `/tmp/CrowdStrike-private` volume per container. The patching utility adds it automatically; the Terraform module (v0.0.2) doesn't, so keep the root filesystem writable there. |
| The sensor doesn't connect | Check that `SYS_PTRACE` is in `linuxParameters.capabilities.add`, that the task has outbound access (a public IP or NAT) to the CrowdStrike cloud, and that the CID includes its checksum. |
| Wrong-architecture errors (`exec format error`) | Match the image architecture to `runtimePlatform.cpuArchitecture`. Use `--platform linux/amd64` on Apple Silicon. For ARM64 tasks, patch with `falcon_image_platform: aarch64` (falconutil) and set `cpuArchitecture: ARM64`. |
| Resource `tags` disappear from a patched task definition | The patching utility drops the task definition's `tags`. Add them back with `jq`, or with `--tags` on `register-task-definition`. |
| A container should not be protected | Add `"dockerLabels": {"sensor.falcon-system.crowdstrike.com/injection": "disabled"}` to that container before patching. |
| A patched image ignores your task definition `entryPoint` | Setting `entryPoint` overrides the Falcon entrypoint baked into the image. Prefix it: `["/opt/CrowdStrike/rootfs/bin/falcon-entrypoint", "<your entrypoint>"]`. Overriding only `command` is fine. |
| Deployment fails because a container is named `crowdstrike-falcon-init-container` | That name is reserved for the Falcon init container. Rename your container. |

## Sensor options

Pass any `falconctl` option, for example `--tags`, `--billing=metered` or `--provisioning-token`, through the method's options input. Each sample shows how:

- `falconutil patch-image --falconctl-opts "--tags=..."` (01)
- `falcon_additional_opts = "--tags=..."` (02)
- `-falconctl-opts "--tags=..."` (03, 04)

For init container tasks the options end up in the application container's `FALCONCTL_OPTS` environment variable. For patched images they're built into the image.
